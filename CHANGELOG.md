# Changelog

All notable changes to this project are documented here. Format based on [Keep a Changelog](https://keepachangelog.com/); this project adheres to Conventional Commits.

## [Unreleased]

### Added
- JVM unit coverage for previously untested bridge classes: `EventStore` (ring-buffer eviction and orientation, newest-first ordering, the `since` cursor, streaming-flag semantics, concurrent add/read), `BatteryMonitor` (an unreadable, out-of-range or throwing battery service must read as `null` — never a guessed number), `ScreenRecorder` (precondition ordering, single-use projection-token handling, the 30 s duration cap, temp-file cleanup, serialised handler-thread state machine), `BridgeNotificationListener` (instance publication on connect/disconnect, the 300-entry cap, parse-or-drop on post, mark-not-delete on remove) and `ScreenNode`/`NodeBounds.computeHash`. 117 tests.
- Three latent defects surfaced by that coverage, each fixed below — the `@Ignore("BUG: ...")` is lifted on every demonstration test, so the test that first reproduced a defect is now its regression test:
  - `EventStore.add()` calls `removeLast()` on an empty deque when `maxCapacity <= 0`, so the first event after such an assignment throws `NoSuchElementException` out of `onAccessibilityEvent` instead of being dropped. Not reachable today (nothing in the app writes `maxCapacity`), but the knob is public.
  - `ScreenRecorder.record()` never releases the `MediaRecorder` when its configuration or `prepare()` throws: `recorder = mr` is assigned only after the `apply {}` block returns, so `cleanupRecording()` in the catch sees a null field and the native recorder (encoder + projection client) leaks. Reachable whenever `prepare()` fails — codec unavailable, storage full, invalid surface.
  - `computeHash()` joins fields with `|` without escaping the separator, so field content containing `|` shifts the layout and two genuinely different nodes hash identically — a hole in the value `/screen_diff` uses to decide nothing changed. Fixing it changes every hash; see Fixed below for the one-time upgrade impact.
- `ScreenRecorder` gained an `internal maxDurationMs` testability seam (default unchanged at 30 s), same pattern as `CommandDispatcher.batteryContext`: the cap is otherwise only observable by waiting out a full capped recording.

### Added
- `GET /battery` — battery percentage and charge state straight from `BatteryManager` (`getIntProperty(BATTERY_PROPERTY_CAPACITY)`, API 21; `isCharging()`, API 23) instead of scraping the status-bar accessibility node, which mis-reads across OEM skins and device languages. Neither value depends on the accessibility service running, and at `minSdk 26` neither needs a version gate. Fixed response shape — `batteryPercentage` and `charging`, both always present — because the HTTP and relay transports serialise nulls differently (#103).

### Changed
- **A public relay host now defaults to `wss://`.** Typing a bare `relay.example.com` into the app used to produce cleartext `ws://`; only an explicit `https://`/`wss://` got TLS. Private hosts (RFC1918, `127/8`, `0/8`, `169.254/16`, `::1`, `fe80::/10`, `fc00::/7`, `*.local`, `*.localdomain`, `*.internal`, `localhost`, single-label names) keep `ws://` exactly as before, and an explicit scheme always wins — so no LAN setup changes. Connecting over `ws://` to a non-private host now draws a toast and a persistent red line on the relay status saying that plaintext can be *injected into*, not just read (TRANS-1).
- **`android_events()` returns an empty list until `android_event_stream(True)` is called.** The streaming switch used to be a report, not a control: the phone buffered the last 200 accessibility events regardless and `GET /events` served them while reporting `streaming: false`. Collection is now gated at the source, which is what the tool descriptions always claimed (DROID-4).
- `android_send_intent`'s schema no longer advertises values the device rejects (`tel:+1234567890`, `android.settings.WIFI_SETTINGS`), and `android_broadcast` no longer suggests a protected system broadcast; the intent description now states the boundary and points at `android_call`/`android_send_sms` (CTRL-2).

### Fixed
- `ScreenNode.computeHash()` length-prefixes each field instead of joining raw values with an unescaped `|`, so field content can no longer shift the layout: `text = "X|Y"`, no description and `className = "C"` hashed identically to `text = "X"`, `contentDescription = "Y"`, `className = "null|C"`. An injectivity hole in the value `/screen_diff` trusts to report "no changes" — and a silent one, since the forged pair reports an unchanged screen. Unlikely to be hit by accident (the neighbouring fields have to be shaped just so), but the separator is attacker-influenced: it comes straight from app-supplied text and content descriptions. **Every hash changes once on upgrade.** Hashes are not stored on-device — `/screen_diff` compares against the `previousHash` the caller supplies — so the only effect is that a hash obtained before the upgrade never matches one computed after it, and the first `/screen_diff` across the upgrade reports "Screen changed" for an unchanged screen. The shape is unchanged (16 lowercase hex chars, first 8 bytes of SHA-256), so no caller or log format needs updating.
- `ScreenRecorder.record()` released nothing when configuring the `MediaRecorder` or its `prepare()` threw: `recorder = mr` ran only after the `apply {}` block returned, so `cleanupRecording()` in the catch saw a null field and the native recorder (encoder + projection client) leaked. Reachable on a real device whenever `prepare()` fails — codec unavailable, storage full, invalid surface — and the next capture then failed with the recorder still held. The recorder is now published to the field before it is configured, so every failure path releases it; the `VirtualDisplay` needed no change, already being assigned the moment it is created.
- `EventStore.add()` no longer throws `NoSuchElementException` out of `onAccessibilityEvent` when `maxCapacity` is 0 or negative. The eviction guard read `size >= maxCapacity` as "at capacity" and called `removeLast()` on an empty deque; a non-positive cap now means "retain nothing" and the event is dropped. Chosen over clamping the cap to 1 because it is the smaller change and honours the knob as written — a floor of 1 would silently retain an event the caller asked not to keep. The volatile knob is read once per add, so a concurrent write cannot desynchronise the guard from the eviction loop. Lowering `maxCapacity` also trims an oversized backlog down to the new cap on the next add instead of serving the old entries until they happen to drain. Surfaced by the new `EventStoreTest` coverage; not reachable in the shipped app, which never writes `maxCapacity`.
- Tool error responses no longer leak the bridge `host:port` or the request URL. 39 of the 40 network tools answered a transport failure with `json.dumps({"error": str(e)})`, and `requests` puts `HTTPConnectionPool(host='…', port=8766): Max retries exceeded with url: /contacts?query=Jane+Doe…` in that text — so a failed call returned the server IP plus, for the GET tools whose arguments travel in the query string, the caller's own PII (`android_search_contacts`' contact name, `android_notifications`/`android_events` params). A single shared `_safe_error()` helper now renders the exception class plus a generic reason (connection refused / timed out / HTTP status) and is used at every error-return site, extending to all tools the redaction `android_mic_fetch` has had since #99. The two message kinds that carry nothing to hide survive verbatim: the bridge's own error body on an HTTP error ("SEND_SMS permission not granted" stays actionable) and any non-`requests` exception (a local `OSError`, a handler's `TypeError`).
- `android_ping` no longer reports `status: "ok"` for a 200 whose body is not JSON. `_extract_response` turns an undecodable body into `{"error": "<raw text>"}` and hands it back as if it were data, so a reverse proxy answering `/ping` with an HTML 502 page produced `{"status": "ok", "bridge": {"error": "<html>502 Bad Gateway</html>"}}`. Agents read `status == "ok"` as "the bridge is healthy" and stop looking — the wrong signal precisely when the relay is returning somebody else's error page. The same now applies to a 200 carrying a JSON `{"error": ...}` body.
- `android_macro` no longer raises on a malformed step. The loop read `step.get("tool")` outside the `try` that turns handler failures into `{"error": "Step N …"}`, so a model that sent `["android_tap"]` or `[null]` instead of `[{"tool": "android_tap", "args": {}}]` got an `AttributeError` out of the tool call — an unhandled exception aborting the agent turn rather than a readable step failure. Steps are now validated inside the per-step error handling (step is an object, `tool` is a string, `args` is an object), and a `steps` argument that is not a list at all is reported too instead of raising `TypeError` from `enumerate(None)` — or, worse, iterating a bare string one character at a time.
- `stop_relay()` no longer raises `RuntimeError("Event loop is closed")` after a failed `start_relay()`. `start_relay()` registered `_relay_instance` before the readiness handshake and left it registered when that handshake timed out (port taken, loop died), while `_run_loop()` closes its loop in a `finally` — so the very next `stop_relay()`, the teardown every caller wraps around a start, called `call_soon_threadsafe()` on a closed loop and blew up instead of shutting down. A failed start now rolls `_relay_instance` back, and `stop_relay()` tolerates a loop that is already closed (including one that closes between the check and the signal) rather than letting the exception escape the caller's cleanup.
- HTTP error bodies are no longer double-encoded in tool responses. `_extract_response()` serialises the bridge's error body into the `HTTPError` it raises so that the text survives, and every caller then filed it under an `"error"` key of its own — producing `{"error": "{\"error\": \"not paired\"}"}`, a JSON document inside a JSON string, for the failure agents most need to read (an unpaired relay, a denied permission). `_safe_error()` now takes the one wrapper back off, so that case returns `{"error": "not paired"}`. Only a body consisting of exactly that single key is unwrapped: a bridge sending `{"error": ..., "code": ...}` keeps both fields rather than having one dropped for tidiness.
- The Python test suite can no longer reach the real `~/.hermes/.env`. `tests/conftest.py` redirected it by setting `HOME` and `HERMES_HOME` to a throwaway directory, but `Path.home()` and `os.path.expanduser("~")` fall back to `pwd.getpwuid(os.getuid()).pw_dir` — the *real* home — whenever `HOME` is absent from the environment, which puts `android_setup()`'s credentials write and `_env_file_vars()`' pairing-token read one `delenv` (or one runner without `HOME`) away from the developer's own files. The autouse fixture now patches the `~` lookups themselves, replacing only the `pwd` fallback so an explicitly set `HOME` still wins, and a regression test asserts the redirect holds with both variables deleted.
- Both transports now answer a route failure the same way. `CommandDispatcher` is documented as the single source of truth shared by the relay and the HTTP server, and both did call it — but only the relay caught. `RelayClient.handleMessage` wrapped `dispatch` and answered `{"error": …}` at `500`; `BridgeRouter` had no `try/catch` and `BridgeServer` installed only `ContentNegotiation`, so an exception escaped to Ktor's default handler as a **non-JSON** 500. A tool that parsed the body therefore worked over the relay and broke over direct USB/LAN for the identical request. `dispatch` now owns the contract — a JSON object with an `error` key at `500` — and `BridgeRouter` guards the routes that run outside it (`/mic_file`). The value is the exception's *class* name, never its message, which can carry an SMS recipient, a file path or a host:port. `ktor-server-status-pages` is not a dependency, so the guard is in the router rather than a `StatusPages` block. Tested at both layers, including a real Netty engine on an ephemeral port answering `POST /open_app` with a JSON 500.
- `android_send_sms` no longer reports success for messages that were never sent. `sendTextMessage(to, null, body, null, null)` passed null for both `sentIntent` and `deliveryIntent`, so no send status was ever observed and `sendSms` returned `ActionResult(true, "SMS sent")` unconditionally — `sendTextMessage` returns as soon as the message is *queued*, not when it is sent. Bodies over the single-segment limit were never divided either, so they failed at the radio layer with nobody listening. An agent sending a 300-character SMS was told it was delivered, told the user so, and — because the recipient and body are stripped from the response by design — had nothing in the tool output to contradict the claim. It now divides with `divideMessage`, sends via `sendMultipartTextMessage` when there is more than one segment, supplies one `sentIntent` per segment, and waits (bounded, 10s) for the radio's report: `success: false` with the named reason on a radio failure, and `success: false` "delivery is unconfirmed" when no report arrives. `POST /send_sms` answers `400` on a blank `to`/`body` — previously it defaulted both to `""`, AOSP threw `IllegalArgumentException` whose message quotes the destination address, and the exception escaped the dispatcher as a 500. The PII convention holds: no outcome echoes the recipient or the body, and the new segment count is the only send detail surfaced.
- The post-revival delayed reconnect now runs on a scope that survives `disconnect()`. `fireTermuxRestart()` launched it on the per-connection `scope`, and when that coroutine fired 30 s later it called `connect()` — whose first statement is `disconnect()`, which does `scope?.cancel(); scope = null`, cancelling the very scope the caller was running on. It only worked because nothing between `disconnect()` and the end of `doConnect()` suspends, so cancelling the enclosing job could not interrupt synchronous code. The first suspension point added to either function — `withContext(Dispatchers.Main)` to update the UI, an `await` on DNS — would make it throw `CancellationException`, abort the reconnect silently, and leave the watchdog firing the script but never reconnecting: the exact bug the call site's comment claimed was fixed. It now launches on an object-level `revivalScope` with its own `SupervisorJob`, and `RelayClientRevivalReconnectTest` drives virtual time through it to prove the reconnect survives a `disconnect()` and that the real `connect()` still reaches `doConnect`.
- The Termux revival watchdog no longer ships one contributor's private deployment path. `RelayClient` hardcoded `/data/data/com.termux/files/home/.termux/boot/start-zee.sh` — a personal stack launcher, in a public repo and a public APK, not configurable and not documented. Any other user who enabled the **Termux Auto-Revival** switch because their relay kept dropping had the bridge fire `RUN_COMMAND` at a script that did not exist on their device: Termux logged an error, the app showed "Stack unreachable — firing Termux revival…", nothing recovered, and the user believed auto-recovery was on. The script is now `RelayClient.DEFAULT_REVIVAL_SCRIPT`, the same location with a project-named script (`start-hermes.sh`); the location is unchanged so the file still doubles as a Termux boot script. No new UI — the path stays a constant, and the docs now say plainly to leave the switch off unless that exact file exists. `docs/configuration.md`, `README.md`, `docs/architecture.md` and a new `docs/troubleshooting.md` section cover the toggle, the *Allow external apps* requirement, the default path and the fire budget. The intent construction moves into `termuxRevivalIntent()` so it is testable: `TermuxRevivalIntentTest` pins the action, target component, all four extras and the path shape, closing the gap where `maybeFireTermuxRevival`/`fireTermuxRestart` had no coverage at all.
- The Termux revival watchdog is now bounded. Its only limits were `WATCHDOG_FAILURES_TO_TRIGGER = 3` and a 10-minute cooldown, and `Fire` reset the counter to 0 — so a relay that was merely unreachable (wrong server URL, rotated pairing code, server down for the weekend) made an opt-in device execute a shell script every 10 minutes indefinitely, each cycle also spawning a delayed reconnect. `RevivalPolicy` gains a fire budget (`maxFires`, default 3 — roughly 30 minutes of automatic recovery) and returns a new `Exhausted` decision once it is spent; a successful connection re-arms it, so a later unrelated outage is not ignored for the rest of the process lifetime. An HTTP 401/403 no longer counts as a watchdog failure at all: restarting Termux cannot fix a credential problem, and spending the budget on one would mask the outage a restart could have fixed. The status line now carries the attempt count (`firing Termux revival (2/3)`) and reports once when the watchdog gives up, instead of the user believing auto-recovery is still running.
- Wake-key test coverage restored (`android_press_key("wake")`, #101). `6fe8444` added three behavioural assertions to `WakeLockManagerWakeTest`; `aa17e70` deleted all three and kept only `assertTrue(wake())`. That is no coverage at all: `wake()` returns `true` unconditionally once a `PowerManager` is present, so the suite passed for any `acquireWakeLock()` that did not throw — including one that acquires nothing, one that drops `ACQUIRE_CAUSES_WAKEUP` (`press_key("wake")` reports `{"success":true}` while the screen stays black), and one that calls `acquire()` with no timeout (the lock is held forever on a device meant to be always-on). The assertions are ported to the Robolectric 4.11 API — `ShadowPowerManager.getLatestWakeLock()` plus `Shadow.extract` for the tag, hold count and `isHeld`, since `Shadows.shadowOf()` has no `PowerManager` overload — and the flags and timeout, which no shadow exposes, go through a new `WakeLockManager.powerManager` test seam modelled on `CommandDispatcher.batteryContext`. Verified by mutation: dropping `ACQUIRE_CAUSES_WAKEUP` and the timeout fails 3 tests, and making `acquireWakeLock()` a no-op fails 7.
- A failed `register_skill` in the plugin is now reported instead of silently swallowed. `register()` wrapped it in `except (AttributeError, TypeError): pass`, justified as "hermes-agent older than the register_skill API" — but `AttributeError` is also what a missing `skill.md` produces and `TypeError` is also what a renamed `path=` kwarg produces. The plugin folder is copied by hand (`install.sh`, the `cp -r` steps in README.md), so a copy without `skill.md` showed `✓ hermes-android v0.5.0 (42 tools)` in `/plugins` while the accessibility-tree-first guidance never loaded — the agent silently regressed to screenshot + vision, the exact behaviour the feature exists to prevent, with nothing in the log to explain it. Each failure mode is now checked separately: `hasattr` for a genuinely old API (info), an `is_file()` check for a broken install (warning naming the path), and `logger.exception` for anything else, so the tools always survive but the reason always reaches the log.
- One source of truth for the Python package version. `setup.py` repeated `version`, `install_requires` and `python_requires` from `pyproject.toml`, and the commit titled `release: v0.5.0` bumped pyproject, `plugin.yaml` and `build.gradle.kts` but left `setup.py` at `0.4.1` — fixed one commit later, with nothing in CI checking either. A release cut from a tree where they disagree publishes metadata whose version depends on the build path: `python setup.py --version` reported setup.py's value while a PEP 517 build read `[project]`. `setup.py` now carries only the packaging hints `[project]` does not express (`packages`, `package_data`) and inherits the rest; `tests/test_version_consistency.py` pins the installed dist metadata, `plugin.yaml` and the APK's `versionName` to `pyproject.toml`, and fails if a `version=`/`install_requires=` returns to `setup.py`. `docs/RELEASING.md` steps 2–3 updated — they did not mention `build.gradle.kts` at all.
- Every documented `ANDROID_*` variable now falls back to `~/.hermes/.env`, and `android_setup` no longer clobbers a port the user configured. `docs/configuration.md` presented all of them under one "Config lives in `~/.hermes/.env`" table, but only `ANDROID_BRIDGE_URL` and `ANDROID_BRIDGE_TOKEN` went through `_env()`; `ANDROID_RELAY_PORT`, `ANDROID_BRIDGE_TIMEOUT`, `ANDROID_RELAY_HOST`, `ANDROID_RELAY_CERT` and `ANDROID_RELAY_KEY` were plain `os.getenv`. That is exactly the process `android_setup` starts the relay in — a gateway that loads `.env` for its own config without exporting it — so `ANDROID_RELAY_PORT=9000` in the file was ignored, the relay bound 8766, and setup then wrote 8766 over the user's 9000. `ANDROID_BRIDGE_TIMEOUT=120` was ignored the same way, timing long `android_wait`/`screen_record` calls out at 30s. `android_relay.py` gets its own `_env()` rather than importing the tool's, so it still runs standalone on a relay host; both copies stay byte-identical. `android_setup` also resolves the file it writes with `_hermes_home()`, the same way the reader does — it used `Path.home()`, so it wrote where nothing looked, and the test suite silently created a real `~/.hermes/.env` on every run.
- `android_send_intent` no longer advertises calls the bridge refuses. Its docstring and schema description recommended `android_send_intent("android.settings.WIFI_SETTINGS")` and promised "setting toggles" — but `ActionExecutor.sendIntent` blocks that action twice over (explicit `blockedIntents` entry plus the `android.settings.` prefix rule), and the `data_uri` hint `tel:+1234567890` used a denied URI scheme. An agent following its own tool description was refused on the first thing it tried, then told the user it could not control the device. The examples are now an `https://` `ACTION_VIEW` deep link, the blocklist is stated in the description, and the working path for settings (`android_open_app("com.android.settings")` then tap) is named. Applied to both `android_tool.py` copies. `tests/test_send_intent_docs.py` derives the advertised examples from the schema and docstring and fails if any is a blocked action or a denied URI scheme, and pins the two copies together.
- `python.yml` now also triggers on `pull_request` for changes to `.github/workflows/python.yml` itself. The path was in `on.push.paths` but missing from `on.pull_request.paths`, so a PR that only edited the workflow — adding a Python to the matrix, changing the pytest invocation — ran no check at all and the breakage landed on `main` to be discovered by the next unrelated PR touching `tools/`. `tests/test_python_workflow.py` pins the two trigger lists together so they cannot drift again.
- Relay route allowlist lifted out of `_serve()` to module level (`_ROUTES`) so tests can assert on it. `docs/architecture.md` is now pinned to the allowlist in both directions, and the two `android_relay.py` copies are pinned byte-identical. An endpoint added to `CommandDispatcher` without the matching allowlist entry used to fail silently: reachable over direct USB/LAN, refused over the relay — which is the default transport (#103).

### Security

Remediation of `docs/refactor/2026-09-29-security-audit.md`. Every High finding, the `.env` injection, the `sendIntent` denylist gaps and the small/local Mediums are fixed, each with a regression test; that document carries a per-finding status line naming the commit, or the reason it was skipped.

- **Pairing-code rotation now takes effect (AUTH-1, High).** `PairingManager` is the single source of truth on the device: the duplicate `relay_pairing_code` store is gone (and cleared from prefs on upgrade), so **Regenerate** drops the live relay session and re-dials presenting the new code, and the UI says which of those happened instead of implying success. On the server, `android_setup` pushes the code to an already-running relay (`start_relay` is a no-op once the thread is alive) and closes any session authenticated with the old one. Before this, an attacker holding a leaked code kept full device control indefinitely after the user "rotated" it.
- **Password fields are redacted instead of serialised (PII-1, High).** `AccessibilityNodeInfo.isPassword` was not consulted anywhere, so a login screen driven by the agent put the user's password — or the OTP the IME had just auto-filled — into `/screen`, `/find_nodes`, `/describe_node` and `/events`, and from there into the transcript and the model provider. One choke point (`security/SensitiveText`) now emits `"[redacted]"` for those nodes, drops their `contentDescription`/`hintText`, keeps the node itself addressable (id, class, bounds, editable) and flags it `password: true`; text searches match the redacted value, so `/find_nodes` cannot be used as an oracle. Screenshots and screen recordings are pixels and remain unredacted — documented in SECURITY.md.
- **Plaintext transport is no longer the silent default (TRANS-1, High)** — see Changed. SECURITY.md's threat model now says what plaintext actually costs: a `ws://` WebSocket has no integrity protection, so an on-path attacker can append frames to the established stream and have the phone dispatch them as authenticated commands, without holding the pairing code at all.
- **`android_setup` validates the pairing code (PY-1).** The value was interpolated raw into `~/.hermes/.env`, which is parsed as `key=value` lines and read back by `_bridge_url()` — so one crafted argument could re-point every later tool call at an attacker host *with the real Bearer token attached*. Codes must now match the alphabet and length the phone generates (`[A-HJ-NP-Z2-9]{6,32}`), the rejection message never echoes the credential, `_update_env_file` independently refuses CR/LF values and non-`NAME` keys, and the write is atomic at `0600` from creation instead of write-then-chmod (which left the token world-readable in between). The fallback path also honours `HERMES_HOME`, matching where the token is read from.
- **`sendIntent` denylist gaps closed (CTRL-2).** `sms:` and `mms:` join the blocked schemes; the `content://` prefix list grows from two entries to fourteen (SMS, MMS, MMS-SMS, call log, telephony, contacts, ICC and the AOSP authorities); and the URI is trimmed and lower-cased before the check, so `" tel:+19005550100"` and `"  content://sms/inbox"` are no longer bypasses.
- **MEDIA temp files are deleted (PY-2).** Screenshots, screen recordings and microphone WAVs were written with `delete=False` and never cleaned up, leaving rendered content from arbitrary apps in the temp dir for the lifetime of the filesystem. They are now registered on creation, deleted at process exit, and stale leftovers from crashed runs are swept once per process — without ever touching a file another session may still be relaying.
- **`/wait` and `/screen_record` durations are clamped (RES-1).** An unclamped `timeoutMs` let a malicious relay (or anyone who can inject into a plaintext session) park a coroutine walking the accessibility tree every 500 ms for ~24.8 days, long after the caller's own 30 s timeout. `/wait` is now capped at 120 s — above every timeout a legitimate caller can observe — and `/screen_record` gained the minimum clamp it was missing, so a negative duration is rejected at the boundary instead of throwing inside `Thread.sleep`.
- **A non-ASCII `Authorization` header is a counted rejection, not a 500 (AUTH-5).** `hmac.compare_digest` raises on non-ASCII `str` and neither relay call site was wrapped, so garbage traffic produced an unauthenticated 500 *and* skipped the rate-limit accounting. Both now compare UTF-8 bytes through a helper that cannot raise.
- **SECURITY.md and README describe the shipped product (DOC-1).** The capability list was five items; the real surface includes microphone recording, screen video, SMS, calls, contacts, GPS, clipboard read/write, notifications including dismissed ones, event history, arbitrary intents and broadcasts, and Termux script execution — now a capability → endpoint → permission table. "The phone is never directly exposed" was false (`:8765` binds `0.0.0.0` at app start with no toggle) and is corrected.
- Test-suite hygiene found while fixing the above: the Kotlin suite was red on a clean checkout because `runTest`'s 10 s real-time dispatch timeout tripped on cold mockk proxy generation, and `pytest` was overwriting the developer's real `~/.hermes/.env` on every run.
- `dataUri` is now redacted in the relay's DEBUG request-body log. `android_send_intent` sends the URI under `dataUri` — a key `_SENSITIVE_BODY_KEYS` did not contain — so a `SENDTO` deep link logged `smsto:<full phone number>` verbatim and an `https` one could leak an embedded reset token, against the AGENTS.md rule to strip phone numbers and recipients from responses and logs. `docs/troubleshooting.md` tells users to raise the log level to DEBUG to inspect commands, so this was the default path to a phone number in a log file. `action` and `packageOverride` stay readable: they name a verb and an app, not a person. A new test derives the payload keys from `android_send_intent` itself, so a field added later fails until it is classified rather than leaking by default.

## [0.5.0] - 2026-09-05

### Added
- Termux auto-revival watchdog (#100): after repeated relay failures, an **opt-in** (default OFF) switch fires the Termux `RUN_COMMAND` intent to restart the stack, then schedules a delayed reconnect. Pure `RevivalPolicy` gate/counter/cooldown logic with unit tests; `SecurityException` surfaces visibly instead of being swallowed.
- `include_removed` option on `android_notifications` (#100): dismissed notifications are retained on-device but excluded by default — callers must opt in explicitly to read notifications the user has cleared.
- Notification buffer raised from 100 to 300 entries (#100).
- `android_press_key("wake")` turns the screen on via a short auto-releasing wake lock. `power` is unchanged and still opens the long-press power dialog (#101).
- `android_*` tools fall back to reading `ANDROID_BRIDGE_URL`/`ANDROID_BRIDGE_TOKEN` from `~/.hermes/.env` when the gateway process does not export them (`os.environ` still takes precedence) (#101).
- Four microphone tools (`android_mic_record`, `android_mic_stop`, `android_mic_status`, `android_mic_fetch`) with relay-routed binary WAV streaming and `MEDIA:` delivery.
- Recorder state reporting and atomic `.part` → `.wav` finalization so interrupted recordings are never advertised as complete.
- Keep-last-10 retention for completed WAV recordings.

### Fixed
- Mic recorder state machine can no longer stick at `starting` after an early STOP or service destruction — `/mic_start` returned 409 until app restart before (#98).

## [0.4.1] - 2026-08-09

### Fixed
- relay reconnect: an unreachable server address retried forever. Each failed attempt fired `onFailure`, which cancelled the retry coroutine and started a new one with a fresh counter, so the 5-attempt cap was never reached and the UI stayed stuck on "Connecting…". Attempt count and exponential backoff now live in a `ReconnectPolicy` whose budget survives across callbacks. The budget is refilled only by a user-initiated Connect or by a session that stayed up ≥60s — reaching `onOpen` is not enough, so a relay that accepts the socket and immediately drops it (wrong pairing code) also stops instead of flapping forever. Callbacks from superseded sockets are ignored via a generation guard, `onClosed`/`onFailure` for one dead socket can no longer schedule two attempts, and the exhaustion path retires the socket so a late callback can't overwrite the "Tap Connect to retry" status
- version string on the main view was hardcoded to `v0.2.0` in both portrait and landscape layouts; now dynamically reads from `BuildConfig.VERSION_NAME`

# Changelog

All notable changes to this project are documented here. Format based on [Keep a Changelog](https://keepachangelog.com/); this project adheres to Conventional Commits.

## [Unreleased]

### Added
- `GET /battery` — battery percentage and charge state straight from `BatteryManager` (`getIntProperty(BATTERY_PROPERTY_CAPACITY)`, API 21; `isCharging()`, API 23) instead of scraping the status-bar accessibility node, which mis-reads across OEM skins and device languages. Neither value depends on the accessibility service running, and at `minSdk 26` neither needs a version gate. Fixed response shape — `batteryPercentage` and `charging`, both always present — because the HTTP and relay transports serialise nulls differently (#103).
- JVM unit coverage for previously untested bridge classes: `EventStore` (ring-buffer eviction and orientation, newest-first ordering, the `since` cursor, streaming-flag semantics, concurrent add/read), `BatteryMonitor` (an unreadable, out-of-range or throwing battery service must read as `null` — never a guessed number), `ScreenRecorder` (precondition ordering, single-use projection-token handling, the 30 s duration cap, temp-file cleanup, serialised handler-thread state machine), `BridgeNotificationListener` (instance publication on connect/disconnect, the 300-entry cap, parse-or-drop on post, mark-not-delete on remove) and `ScreenNode`/`NodeBounds.computeHash`. 117 tests.
- Three latent defects surfaced by that coverage, each fixed below — the `@Ignore("BUG: ...")` is lifted on every demonstration test, so the test that first reproduced a defect is now its regression test:
  - `EventStore.add()` calls `removeLast()` on an empty deque when `maxCapacity <= 0`, so the first event after such an assignment throws `NoSuchElementException` out of `onAccessibilityEvent` instead of being dropped. Not reachable today (nothing in the app writes `maxCapacity`), but the knob is public.
  - `ScreenRecorder.record()` never releases the `MediaRecorder` when its configuration or `prepare()` throws: `recorder = mr` is assigned only after the `apply {}` block returns, so `cleanupRecording()` in the catch sees a null field and the native recorder (encoder + projection client) leaks. Reachable whenever `prepare()` fails — codec unavailable, storage full, invalid surface.
  - `computeHash()` joins fields with `|` without escaping the separator, so field content containing `|` shifts the layout and two genuinely different nodes hash identically — a hole in the value `/screen_diff` uses to decide nothing changed. Fixing it changes every hash; see Fixed below for the one-time upgrade impact.
- `ScreenRecorder` gained an `internal maxDurationMs` testability seam (default unchanged at 30 s), same pattern as `CommandDispatcher.batteryContext`: the cap is otherwise only observable by waiting out a full capped recording.

### Changed
- **The relay URL scheme you type is the scheme the app dials — and `android_setup` now prints one.** `RelayUrl` maps `https://`/`wss://` → `wss://` and everything else, including a bare `relay.example.com` or `203.0.113.7:8766`, → `ws://`: the behaviour every stored URL already relies on. An intermediate rule on this branch defaulted a bare *public* host to `wss://`, and it is reverted here because the relay only terminates TLS when `ANDROID_RELAY_CERT`/`ANDROID_RELAY_KEY` are set while `android_setup` told the user to type a bare `public_ip:port` — so the documented setup, and every bare URL already in prefs, failed the TLS handshake against a plaintext listener. The phone cannot know whether the operator configured a certificate; the operator can, so `android_setup` now prints `wss://ip:port` when the relay has one and `ws://ip:port` when it does not, and `get_relay_url()` reports `https://` for a TLS relay instead of hardcoding `http://` (RELAY-2). What TRANS-1 actually needed is kept: `ws://` to a non-private host still draws a toast and a persistent red line on the relay status saying that plaintext can be *injected into*, not just read. Tests: `RelayUrlTest`, `RelayClientBuildWsUrlTest`, `TestRelayUrlScheme`, `TestAndroidSetup`.
- **`android_events()` returns an empty list until `android_event_stream(True)` is called.** The streaming switch used to be a report, not a control: the phone buffered the last 200 accessibility events regardless and `GET /events` served them while reporting `streaming: false`. Collection is now gated at the source, which is what the tool descriptions always claimed (DROID-4).
- `android_send_intent`'s schema no longer advertises values the device rejects (`tel:+1234567890`, `android.settings.WIFI_SETTINGS`), and `android_broadcast` no longer suggests a protected system broadcast; the intent description now states the boundary and points at `android_call`/`android_send_sms` (CTRL-2).

### Fixed
- The loopback TLS warning suppression no longer silences warnings for the whole gateway. `_bridge_tls_verify()` called `urllib3.disable_warnings(InsecureRequestWarning)`, which rewrites the **process-wide** `warnings.filters` list and never restores it. This module runs inside a long-lived gateway, so one `android_ping()` against an `https://localhost` bridge silenced `InsecureRequestWarning` for every other library in the process that makes an unverified HTTPS call — including one that never made the loopback decision this code made and would have wanted to hear about it. A module that relaxed verification for its own one URL should not also be the reason nobody else hears about theirs.
  The suppression is now `warnings.catch_warnings()` scoped to the single request, in `_loopback_tls_warnings_suppressed()`, and the process filter list is byte-for-byte unchanged after a call. All four bridge call sites go through a new `_bridge_request(verb, url, **kwargs)` that applies both the `verify` decision (F19) and this scope, so a new call site cannot forget either. It attaches the bridge auth headers and is documented as bridge-only: `_get_public_ip()`'s calls to third-party IP-echo services deliberately do **not** use it, since routing them through it would send the pairing token to api.ipify.org. Tests: `TestBridgeTlsVerification` (20 → 26) — `warnings.filters` is unchanged after an https-loopback ping and after a plaintext one, no `ignore` filter for `InsecureRequestWarning` survives, and the context manager suppresses a warning raised inside it while one raised immediately after is still recorded. Red-green verified with the context manager inert: 4 fail.
- The post-revival reconnect now checks itself, not just the flag. F11 gave the woken coroutine one guard — `shouldReconnect` — and F25 moved that guard and the dial into a single critical section. But the coroutine wakes from its 30 s delay and then has to *wait for the monitor*, and `disconnect()`/`connect()` are both `@Synchronized`: a user who disconnects and then reconnects while it was queued leaves `shouldReconnect` **true**, because their own `connect()` set it. The flag-only guard then read "go ahead" for a job that had been cancelled and a URL the user had already replaced, and dialled the old relay over the top of the connection they had just made. That is F11 again, one lock acquisition later.
  `revivalReconnectMayDial(self)` is now the guard, and it answers false unless the job is uncancelled, is still the handle `reconnectDelayed()` last published, and the flag is armed. The coroutine takes its own `Job` from `coroutineContext` and passes it in, still inside the monitor the dial runs under, so F25's one-step property is unchanged. `revivalReconnectJob` becomes internal so the states it passes through can be pinned. Tests: `RelayClientRevivalReconnectTest` (7 → 12) — a user reconnect leaves the flag armed but the stale job may not dial; a job cancelled while it waited may not; a job superseded by a newer watchdog fire may not, while the newer one may; a cleared handle may not; a null job may not. The five pre-existing F9/F11/F25 cases still pass, including the two that exercise the wired path end to end. Red-green verified with the predicate reduced to the flag alone: 4 fail.
- The relay's WebSocket handshake reads the expected pairing code once. `_handle_ws` compared the presented token against `state.pairing_code` and then, a few lines later, read `state.pairing_code` again to record which code the session had proved. `set_pairing_code()` runs on the caller's thread and needs only `_relay_lock`, which the handler never holds, so a rotation could land between the two reads — and the session that had proved the OLD code was recorded as having proved the NEW one. F21's post-`prepare` re-check then compared NEW against NEW, passed, and published the session; the scheduled rotation drop compared the recorded code against the current one, found them equal, and left it alone. The result was the thing rotation exists to prevent: a session holding full device control on a code that no longer exists, indistinguishable from a legitimate one, with nothing in the log to show it. F21 closed the window between the check and `prepare`; this closes the one inside the check itself. `expected_code` is now read once and used for both the constant-time comparison and `authenticated_with`. Both copies. Tests: `TestRotationDuringHandshake` (3 → 4) — a hook on `_tokens_equal` rotates the code immediately after the first comparison, which is the only deterministic way to land inside the gap, and the session must then be closed with `POLICY_VIOLATION`, never published, never recorded, and never serve a command; before the fix it is published recording the new code.
- `android_send_sms` only calls a send retryable when every segment accounted for itself. `describe` mapped any failure code with nothing confirmed to `status: "failed"` — documented to the agent, in the schema, the docstring, `skill.md` and `docs/troubleshooting.md`, as "nothing went out, a retry is safe". But a failure code arrives as soon as *one* segment reports: a three-segment send where segment one hit `RESULT_ERROR_RADIO_OFF` and segments two and three never answered at all produced exactly the same answer, and the two silent segments may well have gone out. The retry the caller was told was safe then duplicated them. F23 drew the line at "did any segment succeed"; the line also has to be "did every segment report".
  `describe` now takes `reportedParts` — the tally F29 made complete — and `failed` requires `reportedParts >= parts`. A failure with segments unheard from falls back to `queued_unconfirmed`, `success: true`, do-not-resend, and wording that still names the radio's reason *and* how much of the tally is missing ("1 of 3 segments reported and at least one failed (radio off), the rest never reported"), so the agent can tell the user something went wrong without being invited to resend. Both new parameters default to 0, which is the safe direction: an unstated tally can never produce `failed`, so a caller that forgets to pass it degrades to do-not-resend rather than to a duplicate. `ActionExecutor.sendSms` passes `report.reportedParts` alongside `report.confirmedParts`. The four statuses and the tightened meaning of `failed` are restated in the schema description, the docstring (both copies), `skill.md`/`SKILL.md` and `docs/troubleshooting.md`. Tests: `SmsSendReportTest` (25 → 28) and `ActionExecutorSendSmsTest` (16 → 17) — a failure with unreported segments is `queued_unconfirmed` and not retryable, `failed` appears only at `reportedParts == parts` (asserted across all four values for a 3-segment send), the same through a real `SmsSendReport` whose bound runs out, and end to end through the executor with a two-segment send that hears from one. Red-green verified with the parameter inert.
- A multipart SMS whose segments all reported now answers immediately instead of sitting out the whole ten seconds. F23 made a multipart send wait for the remaining segment reports so the confirmed tally would be complete, but a failed report never counted the latch down — it recorded the code and returned. The latch therefore only reached zero when every *successful* report had arrived, so a three-segment send that got two OKs and one failure, i.e. every report the radio was ever going to send, still waited out `smsSendReportTimeoutMs` for a count that could never be released. Ten seconds of a caller's 30 s budget on the common failure path, on a `Dispatchers.IO` thread F13 had just moved it onto.
  Every report now counts down, success or failure, and the failure codes are recorded separately: `failure` keeps the first code (the one reported), a new `rejected` counter tallies them, and `reportedParts` is `confirmedParts + rejected`. The latch now means what the wait needs it to mean — "every segment has reported" — so it ends when the tally is actually complete and only runs to the bound when a report genuinely never arrives. A single-segment send is unchanged: one report, one count down, immediate. `reportedParts` is also what the next fix needs to tell a complete tally from an incomplete one. Tests: `SmsSendReportTest` (22 → 25) — the mixed multipart case and the all-failed one both assert they answer in under a second against a 5 s bound, `reportedParts` counts successes and failures alike, and a single-segment failure is still immediate.
- The MEDIA temp-file registry is bounded by what is on disk, not by how long the process has been up. F18 made the stale sweep repeat, but `_media_temp_files` was still only ever added to: `_register_media_temp()` put a path in, and nothing took one out until `atexit` cleared the whole set. A gateway that runs for days therefore accumulated one dead entry per screenshot, screen recording and microphone fetch — small, but monotonic, in the one process that never exits, and atexit then walked a list of paths that had not existed for days. The sweep now prunes it: registered paths whose file is gone are discarded, both for files this pass deleted and for files anything else removed. The prune runs before the directory listing so an unreadable temp dir does not also stop it, and it is wrapped per path so one bad `stat` cannot abort the pass. Files that still exist stay registered — including the one the current call is about to hand back as `MEDIA:<path>`, whose mtime keeps it out of the age-based deletion as before. Both copies. Tests: `TestMediaTempFileRetention` (10 → 14) — a path the sweep deleted is unregistered, a path that no longer exists is unregistered while a live one is kept, five successive registrations leave the registry empty rather than holding five dead paths, and pruning still happens when `os.listdir` raises.
- `android_send_sms` no longer spends ten seconds waiting for a report nothing was listening for. Registering the `sentIntent` receiver can fail — a `SecurityException` on a hardened ROM, an `IllegalArgumentException` from a context that cannot take one — and `sendSms` correctly refused to claim success without a report. It then waited out the whole `smsSendReportTimeoutMs` bound for a report that by construction could not arrive, a third of the caller's default 30 s budget spent learning nothing, and answered with the timeout wording ("no send report arrived within 10000ms") — which says the radio was given the chance to confirm and did not, when in fact the bridge never had anywhere to put the answer. The unregistered case now returns immediately through `SmsSendReport.describeUnobservable(parts, reason)`, with wording that says the report cannot be observed on this device and names the reason. The status stays `queued_unconfirmed` and the do-not-resend rule is unchanged, because the message is with the radio either way; the send itself still happens, since an unobservable report is not a reason to withhold it. `docs/troubleshooting.md` documents the variant next to the timeout one. Tests: `SmsSendReportTest` (21 → 22) and `ActionExecutorSendSmsTest` (13 → 16) — the unregistered send answers in under a second of a 5 s bound, the wording is the unobservable one and not the timeout one, the message still reaches the radio, and no `unregisterReceiver` is attempted for a receiver that was never registered. Red-green verified: 2 fail before the wiring.
- The relay's own 500s now carry the same body as HTTP's. L1 made `CommandDispatcher.errorBody()` the single contract for a route failure, and both transports used it — but there is a third 500 site that `dispatch` never sees: `RelayClient.handleMessage`'s catch, which wraps the JSON parse, the `request_id` check and the `/mic_file` stream. That one answered `{"error": e.message}`, so a command with no `request_id` came back over the relay as `{"error": "Command is missing request_id"}` while the identical failure over direct HTTP answered `{"error": "IllegalArgumentException"}`. Same divergence L1 existed to remove, and the leaky side: an exception message can quote an SMS recipient, a file path or a host:port, which is what the PII convention keeps out of responses. The catch now builds its envelope from `CommandDispatcher.errorBody()`. The `Log.e` text is unchanged — logcat already prints the throwable's own message and stack trace, and a device-local log is not a tool response. `docs/architecture.md` names all three 500 sites. Tests: `RelayClientRelayTest` (11 → 13) — the envelope is a bare class name matching `[A-Za-z0-9_$.]+` with no spaces (the same assertion `CommandDispatcherErrorContractTest` makes of the dispatcher), and it is asserted *equal to* `errorBody()`'s output for the same cause rather than to a string, so the two cannot drift again silently. All three fail before the change.
- The post-revival reconnect's guard and its dial are now one step. F11 had the coroutine check `shouldReconnect` and clear its own job handle inside `synchronized`, then call the connector *after* releasing the monitor. `disconnect()` and `connect()` are both `@Synchronized`, so a user disconnect landing in that gap found no job left to cancel and a flag nothing would re-read — and the reconnect went ahead anyway, which is F11 again one instruction narrower. The window was small (no suspension point between the two) but it was on the exact path the guard exists to protect: the 30 s timer expiring while the user is looking at the relay screen. The connector is now called inside the same critical section. The monitor is reentrant, which is what lets the dial call `connect()` — and so cancel this very job — without deadlocking, so F9's "the reconnect must not be cancelled by its own `connect()`" still holds; nothing in the dial blocks on the monitor from another thread (`notifyStatus` posts to the main looper, `newWebSocket` enqueues). Tests: `RelayClientRevivalReconnectTest` (6 → 7) — `Thread.holdsLock(RelayClient)` observed from inside the connector, which is the invariant itself rather than a race replay; it fails before the change. The six F11/F9 cases pass unchanged.
- `android_setup` can now print a `wss://` address the phone can actually complete a handshake with. It printed the detected public IP, and the phone validates the relay's certificate with the platform trust store — which means hostname verification against whatever it dialed. Certificates are issued for DNS names (Let's Encrypt will not issue one for a bare IP), so the TLS setup the previous change documented failed at the handshake for anyone who followed it, with a certificate error on the phone and nothing on the gateway to explain it.
  `ANDROID_RELAY_PUBLIC_HOST` names the host the certificate covers; `_relay_public_host()` falls back to the detected IP when it is unset. It changes only what is printed — the relay still binds `ANDROID_RELAY_HOST` — so the two cannot be confused. When TLS is on and the variable is unset the address stays an IP and the response gains a `server_address_note` saying the handshake will fail unless the certificate covers it and naming the variable to set; the same sentence is appended to `user_instructions`, because that is the text a human reads. A plaintext relay gets no note: an IP is a perfectly good `ws://` host. `docs/configuration.md` documents the variable in the table, in the `.env` scope list, and in the Relay + TLS section. Both copies. Tests: `TestAndroidSetup` (+8) — the configured host reaches the printed address and the instructions, an IP-only TLS address carries the note in both places, a plaintext address carries none whether or not the variable is set, the helper's unset/empty/set fallbacks, and `ANDROID_RELAY_HOST` still decides the bind address.
- `android_send_sms` no longer tells the caller a partly delivered multipart SMS is safe to retry. `SmsSendReport` answered on the first segment report that was not `RESULT_OK`, and `describe` mapped any such code to `status: "failed"` — documented to the agent, in the schema, the docstring, `skill.md` and `docs/troubleshooting.md`, as "the send definitively did not happen, a retry is safe". For a 3-segment message whose first two segments were confirmed and whose third hit `RESULT_ERROR_NO_SERVICE` that is false: the recipient has the opening of the message, and a retry hands them the same two segments again. F14 had just made the *unconfirmed* case non-retryable for exactly this reason and left the partial case on the other side of the line.
  `SmsSendReport` now counts the segments that reported `RESULT_OK` (`confirmedParts`) and `describe` takes the tally, adding a fourth outcome: `partially_sent`, `success: true`, `delivered` of `parts`, the radio's reason, and an explicit do-not-resend. `failed` is reserved for a definite error with **nothing** confirmed, which is the only case where a retry is safe. Every outcome now carries `delivered` alongside `status` and `parts` so a caller can reason about the tally without parsing prose.
  Counting is only useful if the count is complete, so a failure no longer ends the wait early for a multipart send: the remaining segment reports are awaited up to the same 10 s bound. Answering on the first failure could not distinguish "no segment went out" from "the first two did", and undercounting lands on the dangerous side — it produces `failed`, i.e. "retry". A single-segment send still answers immediately, since nothing else can arrive. The wait runs on `Dispatchers.IO` (F13), so it costs latency, not a blocked transport thread.
  The do-not-resend rule is restated wherever an agent reads it: the tool schema description and docstring (both copies), `skill.md`/`SKILL.md`, and a new `docs/troubleshooting.md` entry. Tests: `SmsSendReportTest` (16 → 21) — a partial multipart send is `partially_sent`, `success: true`, do-not-resend, naming the reason and both counts; a failure with nothing confirmed stays `failed` and retryable; a single-segment failure is never partial; a multipart failure waits out the bound so the tally is final; every segment report is counted; and the PII case still holds for the new outcome. Red-green verified with the counter inert.
- The microphone is no longer held open by a recording the service abandoned. F16 settled the *phase* for a record loop cancelled before its body started, but the same job also owns the `AudioRecord` release: it happens in the loop's `finally`, and a coroutine whose body never starts runs no `finally`. `onDestroy` only called `safelyStop`, which stops capture without releasing, and its unconditional release is guarded by `recordingJob == null` — precisely the case this is not. The native recorder stayed held for the life of the process: the microphone-in-use indicator never cleared, and the next `/mic_start` could fail to initialise the microphone. `onDestroy`'s completion handler now releases whatever `AudioRecord` is still held once the job is done, which is a no-op for a loop that ran (its `finally` already released and nulled the field) and cannot pull the microphone out from under a loop that is still writing, because it waits for completion. `recorder` becomes internal so the leak can be asserted: the case that causes it is a job cancelled before dispatch, which no real `AudioRecord` reproduces on demand. Tests: `MicrophoneRecorderServiceStuckStateTest` (10 → 14) — an abandoned job's recorder is released on destroy, the release happens whatever phase was left behind (the leak was never specific to `FINALIZING`), a still-running finaliser keeps ownership until it completes and is then released exactly once, and a destroy with nothing held releases nothing. Red-green verified by removing the release call: 3 fail.
- A pairing-code rotation can no longer be outrun by a handshake in flight. `_handle_ws` validated the Bearer token, then `await ws.prepare(request)`, and only afterwards published `state.phone_ws`. `set_pairing_code()` runs on the caller's thread and needs only `_relay_lock`, which the handler never holds, so the code could rotate inside that await — and the session then published itself with a code that no longer existed. F17's drop could not catch it: it targeted the socket that was current when the code changed, and this one was not current yet. The result was full device control (screen, input, microphone, SMS, calls, contacts, location, clipboard) surviving the rotation that exists to revoke it, with nothing in the log to show it.
  Each session now records the code it proved in `state.phone_ws_code`; `_handle_ws` re-checks it under `phone_ws_lock` after `prepare` and closes the socket with `POLICY_VIOLATION` instead of publishing when it has gone stale. `_cleanup_phone` clears the recorded code with the socket, so a later rotation never judges a session it knows nothing about. And `_drop_phone_after_rotation` is now decided by that recorded code rather than by a captured socket identity: it closes whatever proved a code that is no longer current, needs nothing captured, and is a no-op when the live session is already on the current code — which is what makes it cover both F17 (a session that re-dialed with the NEW code survives) and F20 (a rotation with nothing to drop does not fail a healthy session's in-flight requests). A session whose code was never recorded is dropped: failing closed is the safe answer when the alternative is leaving a possibly-stale session with full device control. Both copies. Tests: `TestRotationDuringHandshake` (3) and a restructured `TestPairingRotationDrop` (6). The handshake cases drive a fake whose `prepare()` rotates the code, which is the only deterministic way to land inside the await: the rotated handshake is closed and never published, an unrotated one still publishes and records its code, and a rejected handshake never reaches the re-check (it is not a second authentication). The drop cases pin close-on-stale, survive-on-current *with its pending request intact*, close-on-unknown-provenance, no-op-when-nothing-is-connected, scheduling, and the unchanged-code early return. 14 of these fail before the fix.
- A pairing-code rotation with no session to drop no longer breaks the session that replaced it. `_drop_phone_after_rotation()`'s `stale_ws is None` branch called `_fail_inflight()` unconditionally, on the reasoning that a caller must not hang on a future whose phone is gone. But nothing being connected *at rotation time* means every request pending when the coroutine runs belongs to a session that authenticated with the **new** code — `RelayClient` re-dials the moment its code rotates, and its first tool call can easily be in flight before the scheduled drop gets to run. Those callers were answered `ConnectionError("Phone disconnected (pairing code rotated)")`, so rotating the code broke a healthy session it had no business touching; the `android_ping()` an agent runs straight after `android_setup` is exactly the call that lands in the window. The branch is now a no-op. A future whose phone really is gone is still failed, by `_cleanup_phone()` on the disconnect path where that belongs. Both copies. Tests: `TestPairingRotationDrop` (5 → 6) — a NEW-code session keeps its socket, stays registered, and keeps its in-flight request pending across a rotation that had nothing to drop.
- `android_setup` no longer writes a bridge URL the TLS relay cannot answer. With `ANDROID_RELAY_CERT`/`ANDROID_RELAY_KEY` set, aiohttp serves the relay's *whole* site over that one `ssl_context` — the `/ws` route the phone dials and the HTTP routes the tools call are the same `TCPSite` — but setup still saved and exported `ANDROID_BRIDGE_URL=http://localhost:<port>`. The listener stopped speaking HTTP, so every tool call failed, including the `android_ping()` an agent runs immediately after setup to check the pairing worked; setup itself reported "Relay is running" and a phone address that connected fine, so nothing pointed at the actual breakage. The previous RELAY-2 change fixed `get_relay_url()`, which has no production callers — the URL that matters is the one setup writes. Both are now derived from the same both-paths TLS rule: `_relay_bridge_url(port, tls)` for `ANDROID_BRIDGE_URL`, `_relay_server_address(host, port, tls)` for the phone, and `_relay_tls_enabled()` reads the two variables directly because setup decides the scheme before it imports the relay module (pinned against `android_relay.is_tls_configured()` so the two predicates cannot drift).
  An `https://localhost` URL still cannot verify: the certificate is issued for the relay's public name, never for `localhost`. `_bridge_tls_verify()` therefore switches verification off for a **loopback** bridge URL only — that hop never leaves the machine, and an attacker who could intercept it already has local code execution and can read `~/.hermes/.env`, the file holding the Bearer token, directly, so this gives up nothing that was not already theirs and is strictly better than the plaintext loopback hop it replaces. Any other `https://` bridge URL (a remote relay, a reverse proxy, a direct phone connection) keeps full verification, and the urllib3 insecure-request warning is suppressed for the single call that needs it (see the F33 entry below — the first version of this silenced it process-wide). All four HTTP call sites go through one `_bridge_request()` helper so a new one cannot forget the setting: `_get`, `_post`, `_check_requirements`' `/ping` probe and `android_mic_fetch`'s streaming download. `docs/configuration.md` and SECURITY.md document the relaxation and how to avoid it. Tests: `TestAndroidSetup` (+9), `TestBridgeTlsVerification` (10) — the scheme follows the certificate in both the exported env and the written `.env`, half a configuration stays `http://`, the two TLS predicates agree across all four combinations, the verify decision is a table over eight URLs, and every call site is observed passing it.
- The stale-MEDIA temp sweep now runs for the life of the process, not once in it. PY-2 added an age-based, prefix-scoped sweep of `android_screenshot_*` / `android_record_*` / `android_mic_*` files older than an hour, behind a `_media_temp_swept` latch so it ran on the first `_register_media_temp()` and never again. That is the wrong shape for the process that actually runs it: a gateway stays up for days, so it cleaned the temp dir on the first screenshot and then kept every later screenshot, screen recording and microphone WAV — rendered content from arbitrary apps, banking balances and message threads, and the pairing code whenever the Bridge app was on screen — on disk until it happened to exit. `atexit` only ever fires for a process that exits. The latch is now a timestamp: `_MEDIA_TEMP_SWEEP_INTERVAL_SECONDS = 60`, so a registration sweeps at most once a minute (the walk lists the whole temp dir, so it cannot run per file) and otherwise behaves exactly as before — our prefixes only, mtime older than an hour only, best-effort, and never a file this call just registered. Applied to both copies. Tests: `TestMediaTempFileRetention` (8 → 10) — the once-per-process case is replaced by one asserting the interval is respected *and* that a pass runs again after it elapses, a case driving the same thing through `_register_media_temp()` (the path the finding is about), and a case pinning that a second pass never deletes the fresh file the caller is about to hand back as `MEDIA:<path>`. Red-green verified by restoring the latch: 2 fail.

- `python.yml` now also triggers on `pull_request` for changes to `.github/workflows/python.yml` itself. The path was in `on.push.paths` but missing from `on.pull_request.paths`, so a PR that only edited the workflow — adding a Python to the matrix, changing the pytest invocation — ran no check at all and the breakage landed on `main` to be discovered by the next unrelated PR touching `tools/`. `tests/test_python_workflow.py` pins the two trigger lists together so they cannot drift again.
- Relay route allowlist lifted out of `_serve()` to module level (`_ROUTES`) so tests can assert on it. `docs/architecture.md` is now pinned to the allowlist in both directions, and the two `android_relay.py` copies are pinned byte-identical. An endpoint added to `CommandDispatcher` without the matching allowlist entry used to fail silently: reachable over direct USB/LAN, refused over the relay — which is the default transport (#103).
- The Python test suite can no longer reach the real `~/.hermes/.env`. `tests/conftest.py` redirected it by setting `HOME` and `HERMES_HOME` to a throwaway directory, but `Path.home()` and `os.path.expanduser("~")` fall back to `pwd.getpwuid(os.getuid()).pw_dir` — the *real* home — whenever `HOME` is absent from the environment, which puts `android_setup()`'s credentials write and `_env_file_vars()`' pairing-token read one `delenv` (or one runner without `HOME`) away from the developer's own files. The autouse fixture now patches the `~` lookups themselves, replacing only the `pwd` fallback so an explicitly set `HOME` still wins, and a regression test asserts the redirect holds with both variables deleted.

### Security

Remediation of `docs/refactor/2026-09-29-security-audit.md`. Every High finding, the `.env` injection, the `sendIntent` denylist gaps and the small/local Mediums are fixed, each with a regression test; that document carries a per-finding status line naming the commit, or the reason it was skipped.

- **Pairing-code rotation now takes effect (AUTH-1, High).** `PairingManager` is the single source of truth on the device: the duplicate `relay_pairing_code` store is gone (and cleared from prefs on upgrade), so **Regenerate** drops the live relay session and re-dials presenting the new code, and the UI says which of those happened instead of implying success. On the server, `android_setup` pushes the code to an already-running relay (`start_relay` is a no-op once the thread is alive) and closes any session authenticated with the old one. Before this, an attacker holding a leaked code kept full device control indefinitely after the user "rotated" it.
- **Password fields are redacted instead of serialised (PII-1, High).** `AccessibilityNodeInfo.isPassword` was not consulted anywhere, so a login screen driven by the agent put the user's password — or the OTP the IME had just auto-filled — into `/screen`, `/find_nodes`, `/describe_node` and `/events`, and from there into the transcript and the model provider. One choke point (`security/SensitiveText`) now emits `"[redacted]"` for those nodes, drops their `contentDescription`/`hintText`, keeps the node itself addressable (id, class, bounds, editable) and flags it `password: true`; text searches match the redacted value, so `/find_nodes` cannot be used as an oracle. Screenshots and screen recordings are pixels and remain unredacted — documented in SECURITY.md.
- **Plaintext transport is no longer the silent default (TRANS-1, High)** — see Changed. SECURITY.md's threat model now says what plaintext actually costs: a `ws://` WebSocket has no integrity protection, so an on-path attacker can append frames to the established stream and have the phone dispatch them as authenticated commands, without holding the pairing code at all.
- **`android_setup` validates the pairing code (PY-1).** The value was interpolated raw into `~/.hermes/.env`, which is parsed as `key=value` lines and read back by `_bridge_url()` — so one crafted argument could re-point every later tool call at an attacker host *with the real Bearer token attached*. Codes must now match the alphabet and length the phone generates (`[A-HJ-NP-Z2-9]{6,32}`), the rejection message never echoes the credential, `_update_env_file` independently refuses CR/LF values and non-`NAME` keys, and the write is atomic at `0600` from creation instead of write-then-chmod (which left the token world-readable in between). The fallback path also honours `HERMES_HOME`, matching where the token is read from.
- **`sendIntent` denylist gaps closed (CTRL-2).** `sms:` and `mms:` join the blocked schemes; the `content://` prefix list grows from two entries to fourteen (SMS, MMS, MMS-SMS, call log, telephony, contacts, ICC and the AOSP authorities); and the URI is trimmed and lower-cased before the check, so `" tel:+19005550100"` and `"  content://sms/inbox"` are no longer bypasses.
- **MEDIA temp files are deleted (PY-2).** Screenshots, screen recordings and microphone WAVs were written with `delete=False` and never cleaned up, leaving rendered content from arbitrary apps in the temp dir for the lifetime of the filesystem. They are now registered on creation, deleted at process exit, and stale leftovers from crashed runs are swept once per process — without ever touching a file another session may still be relaying.
- **`/wait` and `/screen_record` durations are clamped (RES-1).** An unclamped `timeoutMs` let a malicious relay (or anyone who can inject into a plaintext session) park a coroutine walking the accessibility tree every 500 ms for ~24.8 days, long after the caller's own 30 s timeout. `/wait` is now capped at 120 s — above every timeout a legitimate caller can observe — and `/screen_record` gained the minimum clamp it was missing, so a negative duration is rejected at the boundary instead of throwing inside `Thread.sleep`.
- **A non-ASCII `Authorization` header is a counted rejection, not a 500 (AUTH-5).** `hmac.compare_digest` raises on non-ASCII `str` and neither relay call site was wrapped, so garbage traffic produced an unauthenticated 500 *and* skipped the rate-limit accounting. Both now compare UTF-8 bytes through a helper that cannot raise.
- **SECURITY.md and README describe the shipped product (DOC-1).** The capability list was five items; the real surface includes microphone recording, screen video, SMS, calls, contacts, GPS, clipboard read/write, notifications including dismissed ones, event history, arbitrary intents and broadcasts, and Termux script execution — now a capability → endpoint → permission table. "The phone is never directly exposed" was false (`:8765` binds `0.0.0.0` at app start with no toggle) and is corrected.
- `dataUri` is now redacted in the relay's DEBUG request-body log. `android_send_intent` sends the URI under `dataUri` — a key `_SENSITIVE_BODY_KEYS` did not contain — so a `SENDTO` deep link logged `smsto:<full phone number>` verbatim and an `https` one could leak an embedded reset token, against the AGENTS.md rule to strip phone numbers and recipients from responses and logs. `docs/troubleshooting.md` tells users to raise the log level to DEBUG to inspect commands, so this was the default path to a phone number in a log file. `action` and `packageOverride` stay readable: they name a verb and an app, not a person. A new test derives the payload keys from `android_send_intent` itself, so a field added later fails until it is classified rather than leaking by default.
- Test-suite hygiene found while fixing the above: the Kotlin suite was red on a clean checkout because `runTest`'s 10 s real-time dispatch timeout tripped on cold mockk proxy generation, and `pytest` was overwriting the developer's real `~/.hermes/.env` on every run.

## [0.4.1] - 2026-08-09

### Fixed
- relay reconnect: an unreachable server address retried forever. Each failed attempt fired `onFailure`, which cancelled the retry coroutine and started a new one with a fresh counter, so the 5-attempt cap was never reached and the UI stayed stuck on "Connecting…". Attempt count and exponential backoff now live in a `ReconnectPolicy` whose budget survives across callbacks. The budget is refilled only by a user-initiated Connect or by a session that stayed up ≥60s — reaching `onOpen` is not enough, so a relay that accepts the socket and immediately drops it (wrong pairing code) also stops instead of flapping forever. Callbacks from superseded sockets are ignored via a generation guard, `onClosed`/`onFailure` for one dead socket can no longer schedule two attempts, and the exhaustion path retires the socket so a late callback can't overwrite the "Tap Connect to retry" status
- version string on the main view was hardcoded to `v0.2.0` in both portrait and landscape layouts; now dynamically reads from `BuildConfig.VERSION_NAME`
